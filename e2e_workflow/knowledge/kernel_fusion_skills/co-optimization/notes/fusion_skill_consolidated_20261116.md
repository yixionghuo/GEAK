## 1. 两边结论一致的地方（可信度最高）

| # | 结论 | [M] 证据 | [C] 证据 |
|---|---|---|---|
| 1 | **融合本身几乎不带来收益**。融合消除的是等待，不会减少计算量；收益主要来自在融合结构内部做的 kernel 级优化 | 6 个算子单纯融合最多 +5%，3 个低于 1.0×；之后 67%~100% 的收益来自融合内的优化 | 融合能省的上限约等于"少掉的 graph 节点数 × 2 µs" |
| 2 | **在 graph 里，launch 次数不是主要开销** | 去掉 7 次 launch 只省约 1 µs，模型预计是 18.5 µs | graph 中每个依赖小 kernel 实测约 2.0–2.1 µs；profiler 会把它放大到约 4 µs |
| 3 | **基线必须是生产里实际在跑的路径，并且要先做成员单 kernel 调优，作为对等底线** | 同一个 Qwen 融合，对比随手写的链是 1.25×，对比调优过的库 kernel 只有 1.05× | 判定标准是不慢于"成员单独优化"，C09/C07/C04 都卡在这条线上 |
| 4 | **融合后某一段比它单独跑时更慢，是 bug，要先修，不能当成融合的代价** | §4 Hard rule 2，S1 症状 | C04 融合后 HCB 段从 9.8 涨到 11.5（寄存器合并导致） |
| 5 | **同步范围越窄越好；跨 XCD 的 agent/system release 等于一次 L2 写回** | C1：per-CTA system release +54 µs；C2：同一 XCD 内交接不加 fence，只失效 L1，-6 µs | C04 用 acq_rel 做同步，20–90 µs |
| 6 | **不要用 grid barrier，用就绪计数器（readiness counter）或最后到达者合并** | 有 barrier 的骨架只有 0.685× / 0.837× | C09 的 last-CTA ticket 能用，但跨 XCD 时会输 |
| 7 | **规约跨越生产段的切分轴时，无法部分交接**（例如整行 norm、全 K 点积） | 01 §2 条件 1，N1 | C04 整行依赖 80 段 split-K；C07 整行 norm 被 N tile 重复计算 |
| 8 | **改了结构以后，常数必须重新调**；未调常数会让好的结构看起来很差 | Hard rule 3，§2 Step 6 | C09 只搜了 SPLIT_K=8 所以输，加入 2/4 后赢了 1.16× |
| 9 | **不要为了塞进融合 kernel，用另一种 DSL 重写已经调好的生产 kernel** | L39：慢 5–10%，或只跑到 HBM 带宽的 13–19% | C07 自己写的 GEMM prologue 版输给了 aiter 调优过的 GEMM |
| 10 | **只融那些划算的部分**；结构不适合时，把那一段留在 kernel 外面，按 shape 选路回退，这是正当设计 | E6，§4.5 | C09 按 T 选路；C07/C04 应保持不融合 |

## 2. [M] 有、而我们这轮没用上的 lever（新 prompt 要把它们写进去）

按机制分组，只列对单卡、非持久化或轻度持久化融合有用的（`02` 里的编号）：

**结构和依赖**
- **逐条边判断**（01 §2）：(1) 能否部分交接；(2) 生产段运行时消费段要用的引擎是否空闲；(3) 生产段的 wave 数是否大于 1。窗口上限 = (waves−1)/waves × 生产段耗时。窗口小于同步代价的，不做细粒度交接。
- **不能部分交接的边，仍然可能值得融**，理由只有这几种：消费段中不依赖生产段的操作数（权重、scale、描述符）可以提前加载；交接可以留在片上或同一个 XCD 的 L2；可以填充尾部 wave；可以重排 claim 顺序换取复用。如果融合的理由只是"少一次 launch"，基本不成立。
- **N1 整行 norm 的归属方案**，按优先级：(a) 一个 tile 覆盖整行；(b) 生产段发布每行部分平方和，由最后到达者或行 owner 算 scale；(c) 通信之后按"行 × 列块"切分。
- **A10 代数拆分**：后一段中只依赖前面数据的项，提前在等待期间算完（router 收益 +18 pt）。
- **N2 一次读行，串完所有行内操作**（残差、norm、quant、下一层输入）；**N4 把 quant 放到生产段的 epilogue**，向量化（8 列/lane），不要放到消费段的开头。

**交接和同步**
- **G11 最后到达者合并**：适用于任意 split 规约。计数器单调递增（generation × expected），不需要 barrier，也不需要额外的 merge launch。
- **G12 分片少（split-K 2–4）时一轮合并**，不做多级树形规约。
- **C2/B4 同一 XCD 交接**：生产段和消费段的单元映射到同一个 XCD 的计数器上；生产段 `s_waitcnt(0)` + 一个 agent 原子；消费段只失效 L1。
- **C3**：只在数据要跨 die 时才用 write-through（sc0|sc1）；同一 XCD 内用 write-through 反而 +10 µs（L12）。
- **C8**：一个计数器独占一条 64 B cache line，单调递增、不清零；**F8**：被其他 block 写的 buffer 不要加 `const`/`__restrict__`（编译器会把 load 提到自旋等待前面）。

**提前启动和填空闲**
- **A1/A6**：等待生产段之前，先发射权重、scale、描述符的加载和 setup；在 tile 内部等就绪。
- **A7**：只预取本来就要读的字节，不要额外加读；只在已经存在的等待里做预取。
- **A5/G9**：注意 vmcnt 是按顺序排队的。预取放错位置，会被它本想重叠的那次 load 一起 drain 掉。

**配置和资源**
- **E1 按 bucket 选择器**：常数放在 selector 里，按 shape 档位推导；只有结构开关做成 env。
- **E3**：LDS 取各角色生命周期的最大值，不要相加。**E4**：先找出真正卡住的资源（VGPR 还是 LDS），默认设计为 1 wave/SIMD、256 寄存器。
- **B1**：claim 顺序本身就是调优维度，列分组顺序能复用 L2。**B2**：chunk 大小和顺序一起扫。**B11**：先把不均衡的工作切均匀。

**代码生成（读 ISA 和 metadata）**
- F1：常量偏移锚定到运行时 base，避免 LICM spill。F2：统一值放 SGPR。F3：向量化 epilogue。F5：GEMM 外面不要套嵌套循环。F10：load 无条件发射（mask 用法），避免每个 block 一次 vmcnt(0)。F11：默认关闭的分支在编译期去掉。F12：用最宽的 MFMA。
- 每次结构改动后都读 VGPR/AGPR/SGPR/spill/LDS/occupancy。gfx950 上 profiler 报的 VGPR 单位是 2。

**诊断流程（09）**
- 每轮固定流程：区域时间线 → 每个区域的下限（字节 ÷ 7.0 TB/s、FLOP ÷ 实测峰值、串行跳数 × 延迟）→ 选关键路径上"实际耗时 − 下限"最大的区域 → 查症状表 S1–S13 → 每轮只改一个 lever，用编译期开关 → 成对 A/B → 记录。
- **效率 ≥ 0.85–0.9 时，只有减字节才有用**，不要继续调预取深度或流水线。
- 连续 2–3 轮收益低于约 2–3% 的分辨率，就换结构或停止。

## 3. 我们补充、[M] 没有覆盖的部分（来自单卡小算子 decode 场景）

[M] 的案例都是大的持久化 mega 融合；我们的 5 个是 decode 小算子的 2→1 融合。补充如下：

1. **依赖类型 D0–D4，以及各自的标准做法**：
   - D0 本地：直接融；
   - D1 可重算：每个 CTA 自己重算全局量，代替同步（C01 的 rank）；
   - D2 小组规约：少量 split，放在同一个 XCD 交接（C09 SPLIT_K=2）；
   - D3 全局规约：一般不融；
   - D4 广播/复用：重复倍数乘以生产段代价，远小于 2 µs 时才融。
2. **"用重算代替同步"是小算子融合最可靠的手法**。C01 能赢 1.88×，就是因为它完全没有跨 CTA 等待。[M] 主要讲怎么让同步变便宜，我们更强调**能不同步就不同步**。
3. **按"去重后的单位"划分**：按 token 划分，而不是按 (token, slot) 划分。原链第二个 kernel 的切分是建立在"前一个 kernel 已经全部完成"之上的，原样搬进融合 kernel 会引入重算或等待（C01 补充实验：照搬 aiter 的按 pair 划分后变慢，从 8.25 降到 13.37）。
4. **split 数本身就是融合的搜索维度**，起点要包含单独优化的结论。例如单独优化发现"split 应该更少"，融合版就要搜更小的 split（C09）。
5. **先融合还是先优化，顺序本身不重要**，重要的是搜索空间够大：C01 两种顺序最终打平，C09 是靠扩大搜索空间才赢的。这和 [M] 推荐的顺序（先单独调到对等，再融合骨架，再恢复对等，再上融合专属 lever，最后重调常数）不冲突：[M] 的顺序本质上也是在保证搜索空间里包含每个阶段的最优配置。
6. **小 kernel 的计时口径**：比较一律看 graph replay 下的整链时间；成员时间相加不等于整链时间。

## 4. 统一后的方法（新 prompt 的骨架）

```
0. 基线：生产路径 + graph + 按负载 shape 加权；先做成员单独优化（Tier A/B），得到每个 shape 的对等底线
1. 预算与下限：融合上限 ≈ 少掉的节点数 × 2 µs + 中间张量字节 / 7 TB/s；每段的字节/FLOP 下限
2. 逐条边分析：D0–D4 + [M] 的三条件 + "仍值得融的 kernel 级理由"；D3/D4 先尝试改写
3. 设计空间：≥4 个并行划分候选（含"重算代替同步"、"小 split 同 XCD"、"按 shape 选路回退"），
   每个候选算 CTA 数、wave 数、同步范围、重复倍数、寄存器/LDS，选主方案和备选方案
4. 骨架：复用成员已调优的计算主体（不换 DSL 重写）；把每个阶段的调优配置通过 bucket selector 接进来；
   不用 grid barrier；同步范围最窄；计数器单调；读 ISA/metadata
5. 恢复对等：每段在融合 kernel 内的耗时 ≤ 它单独调优后的耗时（用区域时间线或探针测）
6. 融合专属 lever：A1/A6 提前发射、G11/G12 最后到达者合并、C2 同 XCD 交接、N2/N4 行内串联和 epilogue quant、A10 代数拆分
7. 重调常数：结构确定后按 bucket 重扫，搜索空间包含 split 数和划分方式
8. 验收：逐位一致（或声明容差）、graph replay、每个 shape 不慢于底线（不达标的 shape 选路回退）；
   报告五列耗时；fusion-off 对照做归因
停止条件：连续 2–3 轮低于约 2–3%；或下限探针表明已到底；或 D3/D4 无法改写——给出证据后结束
```
